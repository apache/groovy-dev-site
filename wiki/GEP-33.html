GEP-33

Metadata
Number

GEP-33
Title

Functional Literals for Type-Parameter Slots
Version

3
Type

Feature
Status

Draft
Target

Groovy 7.0
Comment

Makes a closure, lambda or method reference that statically compiled code stores in a slot declared with a type parameter, such as E of List.add(E), usable through the functional interface the call binds, while keeping what such a value can do in Groovy 6. Settles GROOVY-10979 and GROOVY-12561. Native lambdas and inference from context are in GEP-34; call syntax on lambdas and coercion proxies is in GEP-35.
Leader

Paul King
Created

2026-11-25
Last modification

2026-11-26
Note
 WARNING: Material on this page is still under development! This proposal is a draft for discussion. The behaviour tables come from running each example on Groovy 5.1.3, 6.0.0, 6.0.1 (GROOVY_6_0_X with #3359) and a build of this GEP in November 2026.

Abstract

Under @CompileStatic, a closure literal passed with list.add { .. } to a List<Supplier<String>> is stored as a plain Closure. The type checker accepted the call, but the erasure of E is Object, so nothing converts the closure, and a statically compiled list[0].get() fails with ClassCastException. Typed lambdas passed the same way behave identically, and method references were rejected.

This GEP fixes that mainly by adding to what is stored. A closure literal or lambda written for a type-parameter slot that the call binds to a functional interface is compiled as a closure class that also implements the interface. The value is still a Closure, with call syntax, delegate, curry, isCase, identity and serialization unchanged, and it is now also an instance of the interface. A method reference for such a slot is compiled for the interface, including where only the call’s assignment, return, cast or enclosing call gives its type. Untyped parameters take their types from the interface.

Most changes are additions: code that did not compile now compiles, a value that failed when read through the interface now works, or there is a new warning. Two are not, and are listed under Compatibility: an untyped parameter can select a different overload, and @PackedClosures(mode = STRICT) rejects closures it accepted. Dynamic code is compiled as before, but run-time behaviour changes in one respect: dynamic code can call the interface’s methods on a closure that statically compiled code stored (section 2.2).

GEP-34 builds on this to give Groovy Java’s model, where a lambda is the same native object wherever it is written and the target of a call can come from its context. GEP-35 lets dynamic code call native lambdas and coercion proxies. The section Where this leads summarises what the three together give.

Motivation

The bug reports

  • GROOVY-10979: a method reference passed for a parameter declared with a type parameter, such as the U of Stream.reduce, was rejected with "parameter type is not a functional interface", although the call binds U to Function<String, Integer>.

  • GROOVY-12561: under static compilation, list.add { 'x' } on a List<Supplier<String>> stores the closure itself, and list[0].get() fails with ClassCastException.

Both have the same root: a functional literal flows into a slot whose erasure is not the functional interface the program means.

Terminology

Functional literal

A closure literal, a lambda expression or a method reference expression, written in the source at the position being typed. A method pointer (x.&m) is not a functional literal; it creates a MethodClosure.

Functional interface

An interface with a single abstract method that is not a public method of Object, as in JLS 9.8.

Type-parameter slot

A parameter, operand or property whose declared type is a type variable, such as E of List.add(E) or T of Box<T>.value. Its erasure is Object or the variable’s first bound, so the bytecode carries no functional interface.

Implementing closure

A closure class that also implements a functional interface, whose abstract method calls doCall. Written C+I in the tables.

Wrapper closure

A closure made from another by andThen, >>, <<, curry, rcurry, ncurry, memoize, trampoline or asWritable.

Design principles

  1. Add, do not remove. A value stored at a site that compiled in Groovy 6 keeps every capability it had, and gains the interface. The exceptions are listed under Compatibility. Anything that removes a capability in exchange for Java’s model belongs in GEP-34, where its benefit is argued.

  2. Literals only. Only functional literals change. A value that already exists, such as a variable of type Closure, keeps its identity; converting it needs as F.

  3. Statically compiled sites only. Only statically compiled code stores implementing closures. Dynamic and @TypeChecked code compile literals as in Groovy 6; the one run-time change is how dynamic code treats an implementing closure it receives (section 2.2).

  4. No options. The representation does not depend on a system property or build setting.

Proposal

1. Where it applies

Under @CompileStatic, a functional literal is targeted when it is written in one of these positions and the type checker binds the slot’s type variable to a functional interface F:

  • an argument for a type-parameter slot (list.add(x), list.set(0, x), map.put(k, x), varargs, constructor arguments);

  • the operand of an operator method whose parameter is a type-parameter slot (list << x);

  • a subscript or property assignment whose setter or putAt parameter is a type-parameter slot (list[0] = x, map['k'] = x, box.value = x, map?['k'] = x), and a named constructor argument (new Box<F>(value: x));

  • a branch of a conditional or elvis expression in any of these positions.

The type variable is bound by the receiver’s type arguments, explicit type arguments, the other arguments as in Groovy 6, and the call’s assignment, return or cast target as GROOVY-12727 already does. For method references only, section 3 adds the enclosing call’s parameter.

A slot is not targeted when the call leaves its type variable as a type variable of an enclosing method or class, as in <T extends Function<String, String>> void fill(List<T> l) { l.add { .. } }. The bound is not the type of the value: at run time T may be a subinterface of the bound, so implementing the bound would only move the failure to the readers of List<Subinterface>. Section 4 warns at such a slot.

list += x is not a targeted site. Since Groovy 6.0.1 it is a compile error, because plus infers List<Object>, which is not a List<F>; GEP-34’s inference makes it compile.

2. Closure literals and lambdas

2.1 Representation

A targeted closure literal or lambda is compiled as an implementing closure:

  • the closure class declares the interface’s abstract method, and its erasure bridge, with the body a coercion proxy for the closure has: the closure is called with its arguments converted and its exceptions translated as closure as F would call it, so a call through the interface behaves as one through the proxy, at about half the proxy’s cost per call. Where those methods cannot be declared, the method calls doCall directly;

  • the stored value is the closure, so call syntax, delegate, owner, curry, memoize, isCase (switch and grep), equals, identity in contains and remove, and serialization behave as in Groovy 6;

  • statically compiled reads through the interface (list[0].get()) work;

  • untyped parameters take their types from the interface, so list.add { it.trim() } and list.add(s → s.trim()) compile on a List<Function<String, String>>.

A lambda at list[0] = λ or box.value = λ is already a native lambda in Groovy 6 and stays one: the rule applies only where Groovy 6 compiles the lambda as a closure. GEP-34 removes that difference.

2.2 In dynamic code

Dynamic code that receives an implementing closure can call the interface’s methods on it, as statically compiled code does: its abstract method (f.apply(x)), and the default methods it inherits and does not override. A method of Closure with the same name wins, as it does for any closure: dynamic f.andThen { .. } selects Closure#andThen(Closure), because the argument is a closure, and returns a composed closure.

A wrapper closure keeps the closure it wraps as its owner, or holds it in a field. Without a rule, a call of apply on the wrapper would fall through to the wrapped closure and skip the wrapper’s own behaviour: f.andThen(up).apply(x) would run only f, and b.curry('x', 'y').apply(p, q) would drop the curried arguments, with no error. So:

  • a wrapper closure answers the abstract method of the interface its wrapped closure implements by calling itself: f.andThen(up).apply(' a ') is up(f(' a ')), and b.curry('x').apply('y') is b('x', 'y');

  • the interface’s default methods are not answered by a wrapper, so g.twice(x) on a composed closure is a MissingMethodException, as in Groovy 6;

  • a chain of wrappers is followed to the closure that implements the interface.

The wrapper is not an instance of the interface, so this applies to dynamic calls only; a statically compiled cast of the wrapper to the interface fails, as in Groovy 6.

Dynamic code does not store implementing closures. The same source compiled dynamically stores a plain closure, so f.apply(x) works on a value statically compiled code built and is a MissingMethodException on the value dynamic code built, where Groovy 6 failed on both.

In dynamic code, a value passed to overloads m(Closure) and m(F) still selects m(Closure), and collect, switch and grep treat it as the closure it is.

3. Method references

A targeted method reference argument is compiled for the interface, as in Groovy 6.0.1. Its type parameter can also come from:

  • the assignment, return or cast target of the call it is passed to: Function<String, String> f = id(String::trim) (GROOVY-12823, #3337);

  • the parameter of an enclosing call, when the call it is passed to is itself an argument: take(id(String::trim)), and through further calls, take(wrap(id(String::trim))) (GROOVY-12825, #3339).

Groovy 6.0.0 rejects all of these, so they are additions. This is the only inference this GEP adds, and it is limited to method references, which had no representation before; GEP-34 generalises it to every functional literal.

A method reference operand (list << String::trim) and a method reference branch of a conditional argument were method closures in Groovy 6.0.0; they stay method closures, with the warning of section 4. Making them native lambdas removes the method closure’s Closure behaviour, so it is in GEP-34.

4. What is not converted, and the warnings

A targeted literal that cannot be compiled as an implementing closure is stored as in Groovy 6, and the type checker reports a warning at the LIKELY_ERRORS level: "the closure is stored as a Closure, not as F: a statically compiled read through F will fail; write 'as F' to convert it". This happens when:

  • the abstract method’s name is a Closure method (call, doCall, isCase, rehydrate, dehydrate, …​), including a generic interface whose erased bridge would override one (interface Caller<T> { T call(T t) }), or a default method of the interface clashes with one (getOwner, …​);

  • the abstract method has its own type parameters;

  • the target is an abstract class, a trait, a sealed interface, or an interface the closure class cannot access;

  • the closure’s parameters do not fit the abstract method.

Runnable, Callable and GroovyCallable need no conversion and get no warning: Closure already implements them, so a read through them works.

A slot whose type is a type variable of the enclosing method or class (section 1) is not targeted, and gets the same warning, worded for the type variable. Groovy 6 stores a plain closure there without a word; the value is neither the type variable nor its bound, and the failure appears in whichever method reads it.

A value of type Closure, a method pointer or a call result in a type-parameter slot is stored as it is, with the same warning. Inference of the type variable treats such a value as Groovy 6 does, so pick(function, closureValue) still infers the common supertype and does not silently choose F.

A warning is chosen over an error because programs that read such values only from dynamic code work today.

5. Raw targets

For a raw target (List<Function>), the interface’s parameters are Object. A typed closure or lambda is compiled as an implementing closure of the raw interface with an unchecked conversion of its arguments, as a typed closure for a raw Function parameter is today. A raw receiver (List) binds nothing, so nothing is converted.

6. Packed closures

An implementing closure has its own class, so GEP-27 cannot pack it. @PackedClosures in its default LENIENT mode and the groovy.target.closure.pack flag leave it unpacked without a word, and WARN mode and the pack report give the reason. STRICT mode reports every closure it cannot pack as a compile error, so code that compiled with 6.0 under STRICT stops compiling. STRICT is opt-in and incubating; this GEP proposes that it keeps its contract and that the error message names the interface and suggests LENIENT.

Groovy 6

Groovy 6.0.1 ships method reference arguments only (#3359). The rest of this GEP is not purely additive (see above), so it targets 7.0. Three parts are additive bug fixes and are 6.0.x candidates on their own: #3336, and #3337 with #3339.

Where this leads

After this GEP, statically compiled code can store closures, lambdas and method references at type-parameter slots and read them back through the interface, and almost nothing that worked in Groovy 6 stops working. What remains different from Java is addressed elsewhere:

  • Two representations of a lambda. list[0] = λ is a native lambda; list.add(λ) is an implementing closure. GEP-34 makes every targeted lambda and method reference native.

  • Inference from context. Lambdas and closures still need explicit types where javac infers them, as in Arrays.asList(s → ..) and List<F> l = [λ]. GEP-34 generalises section 3 to every functional literal.

  • Calling native lambdas and proxies from dynamic code. f(x) fails on a native lambda, which dynamic code already receives from F f = λ and from Java libraries, and on a coercion proxy. GEP-35 adds call syntax for both, and is independent of this GEP and of GEP-34.

Alternatives considered

Native lambdas now (version 1 of this GEP)

Gives Java’s representation at once, but removes call syntax and closure behaviour from values that dynamic code reads today. Moved to GEP-34, with call syntax in GEP-35.

Keep the 6.0 option

Lambdas native only under a JVM system property, so the representation depends on the build. Rejected.

Convert values as well as literals

A new proxy per conversion breaks contains, remove and equals on the stored value. Rejected.

Coerce at the read site

A statically compiled read of an erased slot whose static type is a functional interface would convert a Closure found there, leaving the stored value as in Groovy 6. Weaker than this GEP: instanceof F stays false, Java readers still fail, and a read converts each time unless the conversion is cached per closure. It is the agreed fallback if implementing closures are not accepted, and could sit behind an incubating flag safely: only the reading code changes, so libraries compiled with and without it hand out the same values.

Call doCall directly from the interface method

About twice as fast per call as the proxy-equivalent body, but a wrong argument through a raw view then fails with ClassCastException in the bridge instead of Groovy 6’s MissingMethodException. Neither form honours a metaclass that intercepts the closure on that path. Rejected.

Implement the bound at a type-variable slot

Moves the failure from readers of the bound to readers of a subinterface, with no gain. Rejected in favour of the warning.

A wrapper answers nothing

Restores Groovy 6’s MissingMethodException for apply on a wrapper. Consistent, but leaves f.andThen(up).apply(x) failing where statically compiled code composing through Function works. Rejected in favour of section 2.2.

A compile error instead of the section 4 warning

Sound, but breaks programs that read such values only from dynamic code. Could be added later under a strict mode; GEP-34 makes it an error for lambdas, as javac does.

Open questions

  • Should a closure literal added to a List<? super F> be accepted as an implementing closure of F? Since GROOVY-12714 it is a compile error, because a Closure is not an F. An implementing closure is an F, so accepting it is sound, as Java accepts an anonymous class there.

  • Should @PackedClosures(mode = STRICT) exempt closures that are unpacked only because they implement an interface, so that section 6 is not a break?
